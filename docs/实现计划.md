## 一、需求本质

用户诉求是"**探索风味**"：同一首歌，降调/升调、降速/升速后产生完全不同的听感。核心不是卡拉 OK 式"匹配人声音域"。

关键洞察（来自竞品调研）：

> **现有全部工具只给出 (key, speed) 空间里的一条一维对角线。** 它们都做朴素变速（改 playbackRate，音高跟着塌），**独立调性控制为零**。没人能做"0.85× 速度 **且** −3 个半音"。这个组合能力本身就是产品。

且用户的原话在中国已是**已上线功能**：[酷狗音乐 2022-11 上线调速/升降调](https://baijiahao.baidu.com/s?id=1749728108027565118)（0.5×–1.5×），文案称 0.8× 播放「崭新听感犹如打开了新世界大门」。**需求已被验证**，空位在于：不能下载、不能独立调性、上限 1.5×、不能批量。

### 2.1 横向对比

### 2.2 为什么选 signalsmith-stretch

- **MIT 许可**，无 GPL 顾虑，可商用闭源
- **质量背书**：Geraint Luff 的算法（ADC22《Four Ways To Write A Pitch-Shifter》），**Chromium 的 `HTMLMediaElement.preservesPitch` 用的就是它**，Qt 6.10 也内置
- **`schedule({output, semitones, rate, ...})` 自动化 API** —— 专为"拖滑块不爆音"设计，自动补偿自身延迟。这正是本项目交互的核心
- **流式缓冲管理**：`addBuffers()` / `dropBuffers(t)` 可释放已播放数据 → 长音频不爆内存
- **内建 `loopStart`/`loopEnd`** → A/B 循环零成本
- **共振峰控制**：`formantCompensation` / `formantSemitones` / `formantBaseHz`
- 单文件 114 KB、零依赖、10.9 万次/月下载、560★、2026-09 仍在更新
- **无 SharedArrayBuffer、无 COOP/COEP**

API 速览：
```js
const node = await SignalsmithStretch(audioContext, { channelCount, sampleRate });
node.addBuffers([left, right]);
node.start();
node.schedule({ output: ctx.currentTime + 0.05, semitones: -3, rate: 0.85 });
node.latency();
```

**离线导出**：把同一节点挂到 `OfflineAudioContext` 上 `startRendering()` 即可。**预览与导出同一算法 → 所听即所得。**

> ⚠️ 诚实说明：signalsmith-stretch 我验证到的是**源码 API、许可、发布活跃度、wasm 内嵌与线程特征**；因它是 AudioWorklet 节点，**无法在 Node 里跑基准**，运行时质量需在浏览器里做 spike 验证。已知小问题：#33 输出偏 ±1.2 音分、#32 大幅变调偏升（−24 半音时 +16 音分）。上游文档称**变速在 0.75×–1.5× 之间效果最佳**，变调可跨多个八度。

### 2.3 rubberband-wasm：实测数据与三个坑

虽改为备选，但实测数据（**本机 Node 24，30 s 单声道 44.1 kHz**）仍有价值：

| 用例 | 输出时长（期望） | 实测音高（期望） | 倍速 |
|---|---|---|---|
| 原样 | 30.00 s (30.00) ✅ | 0 st (0) ✅ | 109× |
| 升 7 半音 | 30.00 s (30.00) ✅ | +6.93 st (+7) ✅ | 38× |
| 降 5 半音 | 30.00 s (30.00) ✅ | −5.07 st (−5) ✅ | 39× |
| 速度 80% | 37.50 s (37.50) ✅ | 0.06 st (0) ✅ | 49× |
| 速度 130% | 23.08 s (23.08) ✅ | 0.06 st (0) ✅ | 49× |
| −3 半音 + 85% 速度 | 35.29 s (35.29) ✅ | −2.93 st (−3) ✅ | 37× |

**变调与变速完全独立，行为正确。** 5 分钟立体声整曲 56× 实时。

**三个必须知道的坑（实测踩出，官方 demo 抄不得）：**
1. **`final` 语义是"这是最后一块"**（`1` = 最后）。官方 demo 写反了，照抄会导致整首只剩 1 个块。
2. **只要改音高就必须先跑 `study`**，哪怕 `time_ratio == 1`。不跑则"升 7 半音"静默输出 20.04 s（应 30.00 s），不报错。成本 +30% 时间。
3. **单声道也必须传"指针数组"**（`const float *const *`），否则 `memory access out of bounds` 崩溃。

### 2.4 已排除项（附原因）

- **`sonic-wasm`**：顶层 `import "node:module"`，硬编码 `ENVIRONMENT_IS_NODE = true`，`bun build --target node` 产物 —— **浏览器无法加载**，需 fork 重编译。仅 1 个版本、161 次/月下载、0★。
- **Tone.js `PitchShift`**：源码显示是**双 LFO 延迟线**（Zölzer/H910 血统），非颗粒/非相位声码器。不改变时长，但仅适合单音素材；复音音乐上各分音共用一条延迟线互相拍频。
- **`bungee-pitch-shift`**：README 声称基于 "Signalsmith Audio" 的 bungee（该仓库 404），真实库是 **MPL-2.0**，却以 MIT LICENSE 发布 —— **许可声明错误**。
- **essentia.js**：AGPL-3.0 + 2022 年停更。
- **@ffmpeg/core**：GPL-2.0 + 64 MB。

### 2.5 部署友好性（已实测）

对 wasm 字节级探测：rubberband 与 signalsmith **均无** `SharedArrayBuffer` / atomics / `PThread` / SIMD
→ **不需要 COOP/COEP 响应头，不需要跨源隔离**。任何静态托管均可（GitHub Pages / Cloudflare Pages / Vercel）。

## 三、技术选型

```
框架       Vite 5 + TypeScript + Svelte 5        （零 UI 组件库）
引擎       signalsmith-stretch 1.3.2 (MIT)       实时 AudioWorklet + 离线 OfflineAudioContext
音频 I/O   mediabunny 1.61 (MPL-2.0)             解码 / 编码 / 封装
波形       自绘 Canvas + Worker 预计算峰值金字塔
```

### 3.1 关于 Svelte 5 的组件问题

你问的"用 Svelte 5 就没有拖拽/滑块组件了？"——**恰恰相反，这些本来就不需要组件库**：

| 需求 | Svelte 5 做法 | 工作量 |
|---|---|---|
| 半音/速度滑块 | 原生 `<input type="range">` + CSS 定制（需离散步进和吸附） | ~30 行 |
| 拖拽上传 | 原生 HTML5 drag/drop 事件 | ~20 行 |
| 文件选择 | `<input type="file">` | 0 |
| 循环区拖拽 | `pointerdown/move/up` 手写 | ~60 行 |
| 波形 | **任何框架下都是手写 Canvas**——没有现成库能满足（见下） | ~150 行 |
| 无障碍弹层等 | 需要时用 headless 原语 [`bits-ui`](https://bits-ui.com)（Svelte 5 兼容） | 按需 |

**结论：零 UI 组件库依赖。** 需要组件库的场景（Ant Design / MUI）和本项目正交。

### 3.2 为什么不用 wavesurfer.js（读了 v8 源码）

| 问题 | 影响 |
|---|---|
| 峰值格式是 `max-abs`（源码里 `Math.abs(topChannel[i])`），**不是有符号 min/max 对** | 无法画出正确波形 |
| **没有多分辨率金字塔**，对单一扁平数组做 `slice()` | 深缩放必然块状 |
| 默认 `sampleRate: 8000` → 60 分钟 = **每声道 115 MB** | 内存爆 |
| `normalize: true` 每次渲染 O(N) 全量扫描 | 长文件卡顿 |

**自绘方案**：Worker 算 5 级 Int8 min/max 峰值金字塔（256/1024/4096/16384/65536 采样一级），60 分钟双声道仅 **~3.3 MB**；单条 `Path2D` 批量 `fill()`；按设备像素选金字塔层级。

### 3.3 I/O 层：mediabunny

- 纯 TS、**零运行时依赖**、可 tree-shake（全功能 gzip ~70 KB）
- 容器双向：`.mp4/.m4a/.m4b` `.mov` `.mkv` `.webm` `.ogg` `.mp3` `.wav` `.aac` `.flac` `.ts` `.hls`
- 关键 API：`AudioBufferSink` 直接产出 Web Audio `AudioBuffer`；`AudioSampleSink` 产出裸 PCM 供 Worker 算波形
- **保留原始采样率**（`decodeAudioData` 会重采样到 AudioContext 采样率，静默毁掉 48k 母带）

编码扩展（均 MPL-2.0，v1.61.0）：

| 包 | 体积 | 说明 |
|---|---|---|
| `@mediabunny/mp3-encoder` | 1.7 MB | LAME 3.100 SIMD，**~55× 实时**（浏览器**完全无法**原生编码 MP3，实测 0/1,142,531 ���话支持） |
| `@mediabunny/flac-encoder` | 1.6 MB | libFLAC（BSD-3，无 LAME 式署名义务） |
| `@mediabunny/aac-encoder` | 4.7 MB | FFmpeg **原生** AAC-LC（**非** fdk-aac，无许可雷） |

## 四、交互模型：双轴而非双模式

这是本项目最重要的设计决策。

**所有人都只在 (key, speed) 空间里给一条一维线；我们要给整个二维平面。**

| 控件 | 范围 |
|---|---|
| **速度** speed | 50% – 200% |
| **调性** key | −12 … +12 半音，作为**叠加偏移量** |
| **模式** | 「黑胶模式」：变速时音高同步下降（黑胶机行为），调性滑块在其上叠加<br>「独立模式」：变速只改速度，调性滑块独占音高权 |

- **黑胶模式下调性读数必须实时显示推导后的总音高**（`0.85× → −2.80 st`），否则用户永远学不会两个控件会互相影响
- 三个能力模式显式呈现：**变调不变速 / 变速不变调 / 自由组合**

### 4.1 关键默认值

- **共振峰保持默认关闭。** 它存在的意义是**避免**花栗鼠效应——但花栗鼠正是这位用户在追求的味道。作为明确标注的开关（"自然人声"）而非术语。
- 变速在 **0.75×–1.5×** 效果最佳（signalsmith 上游文档 + 竞品共识 0.65×–1.30×）
- 调性 **±4 半音**内干净，**±6** 有人为痕迹，**±12** 属 lo-fi 风格区间 —— 滑块上标注这些质量分带

### 4.2 参数换算

```
pitchScale = 2 ** (semitones / 12)
timeRatio  = 1 / speed
0.85× → −2.80 半音   1.25× → +3.86 半音   新时长 = 旧时长 / speed
```

### 4.3 预设（竞品实测共识值，直接印在 chip 上）

| 预设 | 速度 | 调性 |
|---|---|---|
| TikTok Slowed | 80% | 0 |
| Slowed + Reverb | 85% | 0 |
| Vaporwave | 65% | −2 |
| Nightcore Reverse | 75% | 0 |
| Nightcore | 125% | 0 |
| Lo-fi | 75% | −1~−2 |

## 六、风险与避坑

### 6.1 要避开的反模式（源自竞品调研）

1. **一个滑块同时管两件事**（Audacity 的 "Change Speed and Pitch"）—— 直接摧毁产品前提
2. **每次改参数就从头重渲染的"预览按钮"** —— 本品类被抄最多的缺陷
3. **拖动时爆音/断点** —— 立刻失去可信度（→ `schedule()` + 30–60 ms ramp）
4. **听之前先强制渲染**（KeyAndBPM 的 Upload→Adjust→Process→Download 流程）
5. **文案自相矛盾**：soundtools 的 slowed+reverb 页面写着"保持原音高，不会花栗鼠"——**在花栗鼠就是卖点的页面上绝不能这么说**
6. **把变调器和变速器拆成两个页面** —— 所有在位者都这么做，这是他们最明显的结构性弱点
7. **不透明的预设 chip** —— chip 上要印 `0.85× · −0 st`
8. **自动检测的调性/BPM 当成权威** —— 都要给 ÷2/×2 修正
9. **把工程术语暴露给普通用户**（Hz、音分当主控件）
10. **超大范围且无质量提示** —— 封顶 ±12 并标注分带
11. **能纯前端做却上传到服务器**（4 个优秀竞品里有 3 个纯前端，并在页面上明说）
12. **注册墙、水印、排队、隐藏体积上限** —— lacuna.fm 把这些"没有"当成卖点宣传

### 6.2 风险表

| 风险 | 影响 | 应对 |
|---|---|---|
| signalsmith 运行时质量未实测 | 中 | **M1 第一件事就是浏览器 spike**：±12 半音、0.65×/1.25× 各听一遍，必要时回退 rubberband |
| 长音频内存 | 60 min FLAC 解码后 PCM 约 1.2 GB | `dropBuffers(t)` 释放已播部分；峰值用 Int8；>20 min 提示 |
| 移动端性能 | iOS Safari 较慢 | 降采样；提示"建议桌面浏览器导出" |
| Firefox `.aac/.m4a` 解码不全 | 部分用户打不开文件 | mediabunny 自带 demuxer + WebCodecs AudioDecoder 兜底 |
| MP3 上限 48 kHz | 96k 母带无法编码 | 先重采样到 48k 并告知用户 |
| LAME 署名义务 | 合规 | credits 页加 lame.sourceforge.io 链接 |

## 附录 A：rubberband-wasm 最小可用骨架（若启用高质量导出）

```ts
const rb = await rubberband.RubberBandInterface.initialize(
  await WebAssembly.compileStreaming(fetch(rubberbandWasmUrl))
);

const state = rb.rubberband_new(sampleRate, channels, 0 /* offline */, 1, 1);
rb.rubberband_set_pitch_scale(state, Math.pow(2, semitones / 12));
rb.rubberband_set_time_ratio(state, 1 / speed);
if (formantPreserve) rb.rubberband_set_formant_option(state, 16777216);
const chunk = rb.rubberband_get_samples_required(state);   // 实测 1024 帧 ≈ 23ms
rb.rubberband_set_expected_input_duration(state, inputLength);

// ⚠️ 坑 3：指针数组，单声道也要这样建
const p = rb.malloc(chunk * 4);
const chPtr = rb.malloc(channels * 4);
rb.memWritePtr(chPtr, p);

// ⚠️ 坑 2：音高或速度有变化时，必须先全曲 study
for (let r = 0; r < inputLength; r += chunk) {
  const n = Math.min(chunk, inputLength - r);
  rb.memWrite(p, channel0.subarray(r, r + n));
  rb.rubberband_study(state, chPtr, n, r + n >= inputLength ? 1 : 0);  // ⚠️ 坑 1
}

while (r < inputLength) {
  rb.rubberband_process(state, chPtr, n, r + n >= inputLength ? 1 : 0); // ⚠️ 坑 1
  while (rb.rubberband_available(state) >= chunk) retrieve(chunk);
}
while (rb.rubberband_available(state) > 0) retrieveAll();
```
